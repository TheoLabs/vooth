Identity & Access

Account · 계정

시스템의 인증·인가 주체(principal). 관리자(ADMIN)와 크리에이터(CREATOR) 계정을 하나의 애그리게이트로 표현하며, 가입 승인 → 활성 → 탈퇴로 이어지는 상태 머신과 역할 부여를 캡슐화한다.

구현됨 admins/accounts AdminGuard (ADMIN) AR · Account

01 책임과 특성

  • RBAC의 주체 — 계정은 정확히 하나의 Role(roleId)을 참조하고, 역할이 권한을 가진다.
  • 타입으로 앱 경계를 가른다 — type(ADMIN/CREATOR)이 어느 앱(back-office·tool / maker)의 계정인지 결정한다. (googleSub, type) 유니크.
  • 상태가 곧 라이프사이클 — 가입은 항상 PENDING으로 시작하고, 승인/거절/탈퇴 전이는 모두 엔티티 메서드 안에서 불변식과 함께 처리된다.
  • 자가 변경 금지 — 역할 변경·탈퇴는 본인 계정에 대해 수행할 수 없다(애플리케이션 정책).

04 비즈니스 규칙 · 불변식

  • 가입은 항상 PENDING — Account.of() 가 무조건 status=PENDING 으로 생성. 클라이언트가 상태를 정하지 못한다.
  • 승인(active) — PENDING 일 때만 가능. ACTIVE 로 바꾸고 동시에 roleId 를 부여한다. (이미 활성/거절/탈퇴면 거부) AccountActivedEvent({accountId}) 를 publish → 아웃박스→CDC→Creator 생성 트리거.
  • 거절(reject) — PENDING 일 때만 가능. REJECTED 로.
  • 역할 변경(changeRole) — ACTIVE 계정만 가능. 상태는 유지하고 roleId 만 교체.
  • 탈퇴(exit) — ACTIVE 계정만 가능. EXITED 로 바꾸고 roleId=null.
  • 본인 보호 — 역할 변경·탈퇴 시 account.id === 대상 id 면 거부(자기 자신 변경 불가).
검토 포인트. 현재 changeRole/active 는 역할 존재만 검증하고 역할 타입(RoleType)과 계정 타입(AccountType)의 정합성은 검증하지 않는다 — CREATOR 계정에 ADMIN용 역할을 붙일 여지가 있다. 또한 목록 검색의 searchKey 는 화이트리스트 없이 컬럼명으로 쓰여, 정책상 검토가 필요하다.

07 가드 동작 (AdminGuard)

보호된 admins/* 호출마다 토큰을 검증하고 ADMIN 계정을 로드해 컨텍스트에 주입한다.

  • Bearer 토큰 부재/위조 → 401.
  • type=ADMIN 계정이 없으면 → 401 (CREATOR 토큰으로 admin 표면 접근 불가).
  • status=EXITED → 403 "퇴사한 계정".
  • roleId 없음(미승인) → 403 "아직 승인받지 못한 계정".
  • 통과 시 ACCOUNT, ROLE 을 요청 컨텍스트에 set.
