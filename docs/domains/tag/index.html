Content · 발행

Tag · 태그

콘텐츠 분류용 전역 태그 마스터. 콘텐츠들이 N:M으로 공유하며, back-office에서 등록·관리한다. usageCount는 연결된 콘텐츠 수의 파생 캐시(이벤트로 재계산).

구현됨 admins/tags AR · Tag hard delete
부분 구현. Tag CRUD(admins/tags)는 구현됨. 단 Content↔Tag N:M(content_tag)과 usageCount 이벤트 재계산은 Content 도메인 대기 — Content 모듈이 없어 현재 usageCount는 0 고정.

01 책임과 특성

  • 전역 태그 풀 — 콘텐츠마다 새로 만드는 게 아니라, 등록된 태그를 콘텐츠가 N:M으로 붙인다.
  • 연결의 소유는 Content — 태그를 다는 행위는 "콘텐츠 편집"이라 join(content_tag)의 owning side는 Content.
  • usageCount는 파생 캐시 — 정렬·인기태그 표시용. 진실의 원천은 join 테이블이고, 이 값은 이벤트로 재계산.
  • 마스터 데이터 — 이력 보존 의무 없음 → 삭제는 하드삭제.

03 color — 자유 문자열

색상은 자유 문자열로 저장한다. (이전 설계의 TagColor enum은 채택하지 않음 — shared에서도 제거됨.) 백엔드는 색을 검증·해석하지 않고, 표시·매핑은 FE 책임이다.

트레이드오프. enum 검증이 없어 임의 문자열이 들어올 수 있다(오타·무효 색 가능). 엄격한 팔레트 제약이 필요해지면 그때 enum 또는 화이트리스트로 좁힐 수 있다.

04 usageCount — 이벤트 기반 재계산 (Content 대기)

  • Content가 태그를 바꾸면 ContentSetTagEvent { addedTagIds, removedTagIds } 발행(예정).
  • Tag 측 @EventHandler가 영향받은 태그를 COUNT로 SET: usageCount = count(활성 Content where tags contains tagId).
  • +1/-1 증분이 아니라 COUNT-SET → at-least-once 재전송·순서꼬임에도 멱등·무drift.
  • 왜 캐시? 태그 목록 인기순 정렬/표시 시 매번 join-count를 피하려는 read 최적화.
현재 상태. Content 모듈·content_tag·이벤트가 아직 없어 핸들러 미구현, usageCount=0 고정. Content 도메인 작업 때 연결한다.

05 라이프사이클 · 삭제

  • 생성 — name(유니크)+color. 동일 name 존재 시 거부.
  • 수정 — name/color 부분 수정(변경 필드만, stripUnchanged). name 변경 시 중복 검사.
  • 삭제 = 하드삭제 — 마스터 데이터라 이력 보존 의무 없음. content_tag FK ON DELETE CASCADE로 연결 자동 정리(Content 생기면). FE는 삭제 전 "연결 N개 작품에서 제거" 경고(usageCount 사용).
Creator와 대비. Creator는 참여 이력 때문에 삭제 금지(영속)인 반면, Tag는 분류 라벨이라 하드삭제가 맞다.
