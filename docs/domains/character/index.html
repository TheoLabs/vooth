Composition · 구성·재생

Character · 등장인물

작품(Content)의 등장인물. Casting(성우 버전)의 부모이자 대사(Line)가 화자로 참조하는 중심축이다. 멀티버전 보이스툰에서 "이 캐릭터를 어떤 성우들이 연기하는가"의 뿌리. 해설(내레이터)도 캐릭터로 둔다.

구현됨 admins/contents/:contentId/characters Content 소속 Casting 부모
구현 상태. CRUD 중 생성·목록·단건·수정 구현됨. 삭제(remove)는 WIP — Casting/참조 가드가 아직 없어 실제 삭제 동작은 미완성(§04). 공유 enum은 packages/shared/src/character.ts. 상위 구성·재생 모델은 Playback 참고.

01 책임과 특성

  • 작품 단위 인물 — 캐릭터는 회차(Episode)가 아니라 Content 소속. 성우는 작품 전체에서 그 캐릭터를 연기한다.
  • Casting의 부모 — 한 캐릭터에 성우 여럿이 붙는다(멀티버전). Character 1:N Casting.
  • 대사의 화자 — Line.characterId가 캐릭터를 참조. 음성 길이는 선택된 Casting의 채택 Recording에서 파생.
  • 해설도 캐릭터 — 내레이션 대사도 Line이라 화자가 필요. NARRATOR 타입 캐릭터로 두어 캐스팅·멀티버전이 그대로 적용된다.

03 type — CharacterType & 정렬

파일: packages/shared/src/character.ts — 문자열 enum + CHARACTER_TYPE_LABEL / CHARACTER_TYPE_ORDER / CHARACTER_TYPES_BY_PRIORITY

값라벨정렬 우선순위
MAIN주연10
SUPPORTING조연20
EXTRA엑스트라90
NARRATOR내레이터95
  • 문자열 enum + append-only — 역할군이 늘면 ENUM 끝에 추가(싼 ALTER). 중간 삽입·재배열(테이블 리빌드) 안 함.
  • 정렬 우선순위는 코드 맵 — CHARACTER_TYPE_ORDER. ENUM 선언 순서에 묶지 않아 역할군 추가에 강함. 10 단위로 띄워 사이 끼움 여지 확보.

정렬 현황

  • order는 type 우선순위의 복사값 — 생성/타입변경 시 order = CHARACTER_TYPE_ORDER[type]로 자동 설정. 즉 같은 type 캐릭터는 order가 동일하다.
  • 목록 정렬은 PaginationDto의 sort/order(프론트 지정)로만 한다. 서버가 FIELD(type) 같은 강제 정렬을 걸지 않는다.
  • 동일 order는 순서를 보장하지 않는다(결정). 같은 type 내 세부 수동 순서/전용 재정렬 API는 두지 않음.
역할군 확장 정책. 추가는 dev 수준(가끔)으로 가정 → enum + 코드 맵으로 충분. 운영자가 배포 없이 직접 추가/순서변경하는 그림이 되면 CharacterRole 룩업 테이블(name, priority)로 승격한다.

04 라이프사이클 · 정책

  • 생성 — back-office 등록(name, type, 선택 description/avatar). content 존재 검증 + 동일 작품 내 name 중복 거부(앱 검사). order는 type 우선순위로 자동. 콘텐츠 상태 무관(상태 가드 없음).
  • 수정 — 콘텐츠가 DRAFT일 때만 허용. 부분 수정(변경 필드만, stripUnchanged), name 변경 시 중복 검사. type 변경 시 order 재설정.
  • 삭제 = WIP — 설계 정책은 "참조(Line/Casting) 있으면 차단"이지만, 현재 가드 미구현(Casting 도메인 대기). 실제 삭제 동작은 아직 완성 전.
앱 레벨 unique의 한계. (contentId, name) 유일성은 DB 제약 없이 앱 검사로만 보장한다(의도). 동시 요청 시 TOCTOU 레이스로 중복이 생길 수 있으나, 내부 어드민 툴 동시성이 낮아 감수한다. 필요해지면 DB unique 추가.
Tag와 대비. Tag는 분류 라벨이라 하드삭제가 맞지만, Character는 대사·캐스팅·녹음이 매달려 있어 참조 무결성을 우선한다.

05 관계 · 경계

  • ← Content: contentId로 소속(논리 FK — 물리 FOREIGN KEY 제약 없음). 애그리게이트 경계 분리 + 서비스 분리 로드맵 대비. 대신 ① 생성 시 content 존재 앱 검증, ② contentId INDEX 필수, ③ 작품 삭제/보관 시 자식 정리는 앱/이벤트 정책으로. (이 규칙은 Episode→Cut→Line→Casting 등 구성 엔티티 전반에 일관 적용)
  • → Casting: Character 1:N Casting(성우 후보 = 버전). 캐스팅·검수·멀티버전의 시작점. Playback §02·§04.
  • ← Line: Line.characterId가 화자로 참조. NARRATOR 포함 모든 대사의 주체.
  • 화면: 등록·관리는 back-office(admins/contents/:contentId/characters). 캐스팅·녹음 화면(maker/tool)은 조회로 참조.
