Character · 등장인물

작품(Content)의 등장인물. Casting(성우 버전)의 부모이자 대사(Line)가 화자로 참조하는 중심축이다. 멀티버전 보이스툰에서 "이 캐릭터를 어떤 성우들이 연기하는가"의 뿌리. 해설(내레이터)도 캐릭터로 둔다.

설계 admins/characters Content 소속 Casting 부모
구현 상태 = 설계. Character는 아직 core-api 모듈로 존재하지 않는다. 본 문서는 합의된 필드·정책을 못 박는 설계 기준이며, 상위 구성·재생 모델은 Playback 참고.

01 책임과 특성

  • 작품 단위 인물 — 캐릭터는 회차(Episode)가 아니라 Content 소속. 성우는 작품 전체에서 그 캐릭터를 연기한다.
  • Casting의 부모 — 한 캐릭터에 성우 여럿이 붙는다(멀티버전). Character 1:N Casting.
  • 대사의 화자 — Line.characterId가 캐릭터를 참조. 음성 길이는 선택된 Casting의 채택 Recording에서 파생.
  • 해설도 캐릭터 — 내레이션 대사도 Line이라 화자가 필요. NARRATOR 타입 캐릭터로 두어 캐스팅·멀티버전이 그대로 적용된다.

03 type — CharacterType & 정렬

파일: packages/shared/src/character.ts (예정) — 문자열 enum

값라벨정렬 우선순위
MAIN주연10
SUPPORTING조연20
EXTRA엑스트라90
NARRATOR내레이터95
  • 문자열 enum + append-only — 역할군이 늘면 ENUM 끝에 추가(싼 ALTER). 중간 삽입·재배열(테이블 리빌드) 안 함.
  • 정렬은 ENUM 순서가 아니라 코드 우선순위 맵 — CHARACTER_TYPE_ORDER. ENUM 선언 순서에 정렬을 묶으면 새 역할 추가가 깨지므로 분리한다.
  • 우선순위를 띄워서(10/20/90/95) 두어 사이 끼움 여지 확보. 조회: ORDER BY FIELD(type, …), name 또는 앱 메모리 정렬.
역할군 확장 정책. 추가는 dev 수준(가끔)으로 가정 → enum + 코드 맵으로 충분. 운영자가 배포 없이 직접 추가/순서변경하는 그림이 되면 CharacterRole 룩업 테이블(name, priority)로 승격한다.

04 라이프사이클 · 삭제

  • 생성 — back-office 등록(name, type, 선택 description/portrait). 동일 작품 내 name 중복 거부.
  • 수정 — 부분 수정(변경 필드만, stripUnchanged). name 변경 시 중복 검사.
  • 삭제 = 보수적 — Line.characterId·Casting이 엮이므로 참조 Line이 있으면 삭제 차단. 대사·녹음이 사라지면 안 되기 때문. (Tag의 하드삭제와 대비)
Tag와 대비. Tag는 분류 라벨이라 하드삭제가 맞지만, Character는 대사·캐스팅·녹음이 매달려 있어 참조 무결성을 우선한다.

05 관계 · 경계

  • ← Content: contentId로 소속. 작품 삭제/보관과 라이프사이클 연동.
  • → Casting: Character 1:N Casting(성우 후보 = 버전). 캐스팅·검수·멀티버전의 시작점. Playback §02·§04.
  • ← Line: Line.characterId가 화자로 참조. NARRATOR 포함 모든 대사의 주체.
  • 화면: 등록·관리는 back-office(admins/characters). 캐스팅·녹음 화면(maker/tool)은 조회로 참조.
