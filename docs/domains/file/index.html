File · 업로드 파일

presigned URL 로 S3 에 직접 올라가는 업로드 파일의 메타. 바이너리는 S3 에만 두고 여기엔 객체 키/메타만 둔다. 핵심 정책은 commit-on-attach — 업로드 직후가 아니라 소유 도메인이 참조하며 저장하는 순간 서버가 확정한다.

구현됨 admins/files AR · File commit-on-attach
소비 도메인. 아바타(Creator)·콘텐츠 썸네일 등이 fileId 로만 참조하고, 표시 URL 은 읽을 때 유도한다. 바이너리 전송은 전부 S3 직접 PUT(서버는 키만 발급/저장).

01 책임과 특성

  • 업로드 파이프라인의 단일 출처 — presign(키 발급) → S3 직접 PUT → 채택 시 commit. 서버는 바이너리를 다루지 않는다.
  • commit-on-attach — isCommit 은 "업로드됨"이 아니라 "채택(참조)됨"을 의미. 소유 엔티티 저장 트랜잭션 안에서 켜진다.
  • 키만 저장, URL 비저장 — full URL 은 환경 의존적(localhost:4566 vs 운영 버킷/CDN)이라 저장하지 않고 getPublicUrl(key) 로 유도.
  • 미채택은 수거 대상 — 채택되지 않은 파일(isCommit=false)이나 교체로 버려진 파일은 cron 이 정리.

04 비즈니스 규칙 · 불변식

  • commit-on-attach — isCommit=true 는 소유 도메인이 fileId 를 참조하며 저장하는 같은 트랜잭션에서만. 별도 commit 엔드포인트 없음.
  • 서버가 HEAD 검증 — commit 시 S3Service.headObject(key) 로 실제 업로드를 직접 확인. 클라의 "업로드 완료" 주장을 신뢰하지 않는다.
  • 형식 제한 — commit(fileId, { mimePrefix }) 로 채택 시 MIME 접두사 검증(예: 아바타 = image/).
  • 멱등 commit — 이미 isCommit=true 면 통과. 되돌리지 않음(단방향).
  • 키 안전성 — prefix 화이트리스트(^[a-z0-9][a-z0-9/_-]*$, .. 금지) + uuid 로 path traversal·충돌 차단. 미지정 시 uploads.
  • 크기 가드 — presign DTO 에서 1 ~ 100MB(sanity cap), MIME 형식 검증.
합성 규칙. commit 은 소유 도메인의 @Transactional 에 합성돼야 원자적이다. 따라서 commit 자체엔 @Transactional 을 붙이지 않는다 — 이 프로젝트의 데코레이터는 전파를 지원하지 않아 중첩하면 트랜잭션이 분리되고 finally 의 컨텍스트 초기화가 바깥 트랜잭션을 손상시킨다.

정리(cron) — 두 규칙 (예정)

  • ① 미채택: isCommit=false & createdAt 오래됨 → 실패/이탈 업로드 → S3 delete + 행 제거. (인덱스로 저렴)
  • ② 교체 고아: isCommit=true 인데 어떤 엔티티도 참조 안 함 & 오래됨 → 아바타 교체 등으로 버려진 파일 → 삭제. (참조 스캔)

내부 API — FileService (다른 도메인이 주입)

메서드용도
presign(input)키 생성 + File 적재 + presigned URL. (컨트롤러도 이걸 사용)
commit(fileId, { mimePrefix? })commit-on-attach seam. 소유 도메인 저장 트랜잭션에서 호출 — HEAD 검증 후 isCommit=true. @Transactional 미부착(호출자 트랜잭션에 합성 — 중첩 시 분리·컨텍스트 손상 방지)
resolvePublicUrl(fileId?)단건 enrich. fileId → string | null. 없으면 null — 호출부 ternary 제거(예: dto.avatarUrl = await fileService.resolvePublicUrl(creator.avatarFileId))
resolvePublicUrls(ids)목록 enrich(일괄, 단일 쿼리). nullable 배열 그대로 받아 필터·중복제거 → Map<id, publicUrl>. N+1 회피
예정. ① creators/* presign(아바타 업로드 — Creator/CreatorGuard 생기면 FileService 재사용), ② 정리 cron, ③ 소비 도메인(Creator) 의 avatarFileId 채택·enrich 연동.

06 의존 · 경계

  • → S3Service (@libs/s3): presigned PUT(createPresignedPutUrl), 채택 검증(headObject), 표시 URL(getPublicUrl), 정리(deleteObject).
  • ← Creator / Content …: fileId 로 File 을 참조하고 FileService.commit 으로 채택, resolvePublicUrls 로 표시 URL 을 유도.
  • 경계: File 은 바이너리·표시 URL 의 출처일 뿐, 도메인 의미(아바타냐 썸네일이냐)는 소유 도메인이 가진다.
