EpisodeCastingReview · 검수 이력(로그)

EpisodeCasting의 검수 전이(요청 → 승인/반려 → 발행)를 시간순으로 남기는 append-only 감사 로그. EpisodeCasting은 현재 상태만 들고 REJECTED↔REVIEWING로 덮어쓰므로, 누가·언제·왜(반려 사유) 했는지의 사이클 이력은 여기서 보존한다.

설계 (구현 추후) creators/* · directors/* append-only audit
구현 상태 = 설계(추후). EpisodeCasting이 먼저 — 이 로그는 그 뒤에 만든다. 단, 이력은 소급 복원이 안 되므로(만들기 전 전이는 유실), EpisodeCasting 구현 시 검수 전이 이벤트를 풍부하게 발행해 캡처는 처음부터 해둔다(§04). 부모는 EpisodeCasting.

01 책임과 특성

  • 검수 이력(audit) — (회차×캐스팅) 검수의 모든 전이(요청/승인/반려/발행)를 1행씩 시간순 기록. "누가·언제·왜".
  • 왜 별도인가 — EpisodeCasting은 현재 상태만(반려→재요청에서 REJECTED→REVIEWING로 덮어씀) → 사이클 이력·반려 사유 히스토리가 사라진다. 로그로 보존.
  • append-only — 생성만, 수정·삭제 없음. 불변 기록.
  • 반려 사유 보존 — 성우가 "왜 반려됐나"를 회차별·사이클별로 확인. (EpisodeCasting엔 최신 rejectReason만 두는 편의 필드, 전체 이력은 여기.)

04 캡처 방식 (구현 시)

  • (A) 이벤트 프로젝션 — 권장 — EpisodeCasting 전이마다 발행하는 도메인 이벤트(ReviewRequested/Approved/Rejected/PublishedEvent, actorId·reason 포함)를 @EventHandler가 받아 로그 행 append. EpisodeCasting 변경 0, 핸들러+테이블만 추가. 전제: ddd_events 보존(보존되면 이미 쌓인 이벤트로 과거까지 복원).
  • (B) 동기 append — 전이와 같은 트랜잭션에서 로그 행 insert. 감사 무결성을 tx로 못 박음(유실·지연 없음). ddd_events 보존이 불확실하면 이쪽.
  • 지금 해둘 것 — 어느 쪽이든 EpisodeCasting 구현 시 전이 이벤트를 actorId·reason까지 풍부하게 발행. 그래야 로그를 추후에 붙여도 이력 손실이 없다(이력은 소급 복원 불가).
