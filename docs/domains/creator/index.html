Creator · 성우

녹음에 참여하는 성우(크리에이터)의 제작 도메인 프로필. Account 와 1:1로 묶이는 독립 애그리게이트로, 계정 승인 시 이벤트 기반으로 생성되며 삭제되지 않는 영속 레코드다(참여 이력 보존).

설계 creators/* · directors/* AR · Creator Account 1:1
구현 상태. 본 문서는 설계 단계다. core-api 에 Creator 모듈은 아직 없고, 생성 트리거인 Account.active() 의 이벤트 발행도 미구현(현재 active() 는 상태만 바꾸고 AccountApproved 를 publish 하지 않음). 구현은 별도 승인 후 진행.

01 책임과 특성

  • 제작 도메인의 주체 — 캐스팅(Character N:M)·녹음(Recording)·채택(LineTake)·정산(Settlement)이 creatorId 로 참조하는 중심.
  • Account 와 1:1 — accountId 유니크로 묶인 독립 애그리게이트. 인증/인가는 Account, 제작 프로필은 Creator 로 경계를 가른다.
  • 이벤트로 태어난다 — 직접 생성 API 가 없다. 계정이 CREATOR 타입으로 승인(ACTIVE)될 때 이벤트로 자동 생성된다.
  • 지워지지 않는다 — 성우가 하차해도 이미 참여한 콘텐츠 이력이 남아야 하므로 hard/soft delete 모두 하지 않는다.
  • name/email 비복제 — Account 가 source of truth. Creator 는 활동명 등 제작 고유 정보만 갖는다.

02 애그리게이트 — Creator (제안)

Account↔Role 패턴을 따른 soft 1:1 (createForeignKeyConstraints: false + accountId unique)

필드타입필수설명
idnumber (PK)✓Creator 고유 식별자. accountId 와 별개 — 캐스팅/정산이 creatorId 로 참조
accountIdnumber · unique✓1:1 soft FK. 멱등성·1:1 의 구조적 보증
nicknamestring✓활동명/예명. 실명(Account.name)과 다른 크레딧 표기용
avatarFileIdnumber | null✓아바타 이미지. fileId 만 저장(key·URL 비저장). File 이 단일 진실, 표시 URL 은 읽을 때 유도 — 아래 §02-1
biotext | null—자기소개
accountAccount—OneToOne soft 관계(물리 FK 없음). name/email 은 여기서 조회
상태 컬럼 없음. 활동 가능 여부는 Account.status 에서 유도한다(중복 저장 금지). 계정 활성과 무관한 "일시 활동 중단" 같은 Creator 고유 상태가 필요해질 때만 availability 추가 검토.

02-1. 아바타 / File 연동 — avatarFileId only

Creator 는 avatarFileId 만 저장한다(key·full URL 비저장). 이유: ① File 이 단일 진실(커밋 검증·고아 정리), ② full URL 은 환경 의존적(localhost:4566 vs 운영 버킷/CDN)이라 저장하면 안 됨 — URL 은 항상 읽을 때 유도.

읽기 — 서버가 URL 로 변환(enrich)

  • 응답 시 avatarFileId → File 조회(key) → S3Service.getPublicUrl(key) 로 avatarUrl 을 만들어 DTO 에 동봉한다.
  • FE 는 fileId 로 재조회하지 않는다 — 응답의 avatarUrl 을 <img src> 에 바로 사용.
  • 목록(캐스팅 피커)은 단일 쿼리 LEFT JOIN file 로 N+1 을 피한다(개별 lazy 로드 금지). File 은 PK 조인이라 저렴.
  • getPublicUrl 은 순수 문자열 조합(DB·S3 호출 없음) — 비용은 key 조회(JOIN)뿐.
응답 DTO 예시. { id, nickname, bio, avatarFileId, avatarUrl } — 저장은 avatarFileId, 노출은 avatarUrl(파생).

쓰기 — presign → S3 PUT → 프로필 저장 시 commit-on-attach

  • ① POST /…/files/presign {originalName, mimeType, size, prefix?} → File(isCommit=false) + presigned PUT URL + fileId.
  • ② FE 가 presigned URL 로 S3 직접 PUT(Content-Type = mimeType 일치).
  • ③ PUT /creators/me/profile { avatarFileId } → 서버가 같은 트랜잭션에서 FileService.commit(fileId, { mimePrefix: 'image/' }) 호출: S3 HEAD 검증 → isCommit=true → creator.avatarFileId 저장.
  • ④ 이전 avatarFileId 의 File 은 미참조 → cron 정리.
commit 엔드포인트 없음. 업로드 직후 별도 /files/:id/commit 을 두지 않는다 — 클라 주장을 신뢰하지 않고, 채택(프로필 저장) 시점에 서버가 HEAD 로 직접 확인해 커밋한다. File 도메인 참고.
트랜잭션 합성 주의. CreatorService.updateProfile 의 @Transactional 단 하나가 트랜잭션을 연다. FileService.commit 에는 @Transactional 을 붙이지 않는다 — 이 데코레이터는 전파(join)를 지원하지 않아 중첩하면 별도 트랜잭션이 열리고 finally 가 Context.ENTITY_MANAGER 를 비워 바깥 트랜잭션을 깨뜨린다. repository 가 컨텍스트 EM 을 읽으므로 commit 은 호출자 트랜잭션에 자연 합성된다.
왜 FileService 를 주입하나. File 은 동급 비즈니스 도메인이 아니라 공용 플랫폼 능력(S3 presign·HEAD·키생성)이라 소비가 정상. 비순환·단방향(Creator→File)이며, Repository 만 주입하면 HEAD/commit/S3 로직이 Creator 로 새므로 service(공개 인터페이스) 주입이 맞다.
구현 상태. File 모듈(admins/files/presign + FileService.commit/resolvePublicUrls)은 구현됨. 단 creator 측 avatarFileId 컬럼·creators/* presign·고아 cron 은 예정.

04 비즈니스 규칙 · 불변식

  • 🔒 삭제 금지 — Creator 는 영속 레코드. 캐스팅/녹음/채택이 creatorId 로 참조하므로 항상 resolve 가능해야 한다.
  • 1:1 보장 — accountId 유니크. 한 계정에 Creator 는 최대 하나.
  • 멱등 생성 — 승인 재호출·at-least-once 대비. accountId 로 이미 있으면 skip(+ 유니크 제약 이중 안전).
  • CREATOR 한정 — AccountApproved 핸들러는 type === CREATOR 일 때만 생성. ADMIN 승인엔 반응하지 않음.
  • 활동 여부 유도 — 하차/활성은 Account.status 로 판단. 캐스팅 피커는 Creator JOIN Account WHERE account.status = ACTIVE.
  • 재활성 시 이력 보존 — 동일 계정이 다시 활성화돼도 accountId 유니크+멱등으로 같은 Creator 재사용 → 과거 참여 이력 유지.
  • name/email 비복제 — Account 에서 조회. 정산 정보도 Creator 가 아니라 별도 Settlement.

05 이벤트 — AccountActivedEvent

승인 시점에 Account 애그리게이트가 발행하는 도메인 이벤트. 아웃박스(ddd_events)에 같은 트랜잭션으로 적재되고 CDC 로 전파된다.

항목내용
payload{ accountId } — 최소 정보. 핸들러가 type=CREATOR 여부 등은 재조회
발행 위치Account.active() 안에서 publishEvent(new AccountActivedEvent({ accountId })) (구현됨)
전파아웃박스 → Debezium CDC → Kafka (in-memory emit 경로 제거됨)
구독AdminCreatorService.@EventHandler(AccountActivedEvent) — CREATOR 계정만, accountId 멱등 체크 후 생성
신뢰성at-least-once · 재시도 3회(백오프) · 소진 시 DLQ(<topic>.dlq). 멱등성은 핸들러 책임

06 API 표면

생성 API 는 없다(이벤트 생성). 본인 프로필은 creators/*(CreatorGuard), 캐스팅 목록은 directors/*.

MethodPath설명상태
GET/creators/me본인 Creator 프로필 조회(avatarUrl enrich, account 조인)구현됨
GET/admins/creators관리자용 Creator 목록(검색·페이지네이션)구현됨
PUT/creators/meavatar/bio/nickname 수정(변경 필드만, commit-on-attach)예정
GET/directors/creators캐스팅 피커용 목록(활동 중 성우)예정
인증. creators/me 는 CreatorGuard(type=CREATOR + status=ACTIVE) 로 보호. 로그인은 Auth 의 POST /creators/auth/login/google/desktop(PKCE).
네임스페이스 규칙. vooth-maker=creators/*(CreatorGuard), vooth-tool=directors/*(DirectorGuard=ADMIN). tool 은 creators/* 를 직접 호출하지 않는다 (CLAUDE.md API 표면 규칙).

07 의존 · 경계

  • ← Account: 1:1(accountId). 승인 이벤트로 생성, name/email/활동여부를 조회.
  • → File: 아바타를 avatarFileId 로만 참조(key·URL 비저장). 읽을 때 JOIN 해 avatarUrl 유도 — §02-1.
  • ← Casting / Recording / LineTake / Settlement: creatorId 로 Creator 를 소프트 참조(삭제 불가의 근거).
  • 정산 분리: 계좌·세금 등은 Creator 가 아니라 별도 Settlement 애그리게이트(creatorId 참조).
