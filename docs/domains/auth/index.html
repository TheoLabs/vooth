Auth · 인증

Google 로그인으로 신원을 검증하고 자체 JWT(access token)를 발급한다. 애그리게이트가 없는 애플리케이션 서비스 도메인으로, Account 를 생성/조회해 인증 흐름을 완성한다.

구현됨 admins/auth · creators/auth No Guard (공개) Google OAuth · JWT

01 책임과 특성

  • 신원 검증 위임 — 비밀번호를 직접 다루지 않는다. Google ID 토큰을 검증해 googleSub/email/name 만 신뢰한다.
  • 최초 로그인 = 자동 가입 — 해당 (googleSub, type) 계정이 없으면 PENDING 상태로 생성(auto-provisioning).
  • 토큰 발급 — 검증 성공 시 { sub: accountId, email } 클레임의 access token 발급. 이후 요청은 AdminGuard 가 검사.
  • 두 가지 클라이언트 — 웹(back-office)은 idToken 직접 전달, 데스크톱(maker/tool)은 PKCE authorization code 교환. (네임스페이스별 컨트롤러 분리)

02 로그인 흐름

웹 (back-office) — ID 토큰 직접 전달

  • ① 프론트가 Google 로그인 → idToken 획득.
  • ② POST /admins/auth/login/google { idToken }.
  • ③ 서버가 GoogleAuthClient.verify() 로 토큰·audience 검증 → 프로필 추출.
  • ④ ADMIN 계정 조회, 없으면 Account.of(...PENDING) 생성·저장.
  • ⑤ access token 발급 → { data: { accessToken } }.

데스크톱 (maker/tool) — PKCE

  • Electron 이 시스템 브라우저 + loopback redirect + PKCE 로 code 수신.
  • 서버가 GoogleAuthClient.exchangeCode({ code, codeVerifier, redirectUri }) 로 교환 → id_token 검증.
  • client secret 은 서버에만 보관(데스크톱 앱에 노출하지 않음).
audience. verify() 는 웹 clientId 와 데스크톱 desktopClientId 를 모두 허용 audience 로 넣어 한 검증기로 두 클라이언트를 처리한다.

03 비즈니스 규칙 · 정책

  • 가입 상태는 PENDING 고정 — 로그인만으로 접근 권한이 생기지 않는다. 관리자가 승인(active) 해야 roleId 가 생기고 가드를 통과한다.
  • 타입 분리 — admin 로그인은 type=ADMIN 계정만 조회/생성. (creator/director 표면은 각자 네임스페이스에서 동일 패턴.)
  • 실패 응답 — 토큰 위조/만료 또는 필수 클레임(sub·email·name) 누락 시 401("유효하지 않은 Google 토큰").
  • 트랜잭션 — 로그인(조회+생성)은 @Transactional().
CLAUDE.md 규칙. 데스크톱 앱은 웹 idToken 로그인 엔드포인트를 만들지 않는다. maker=creators/auth/login/google/desktop, tool=directors/... 의 PKCE 만 사용.

04 API 표면

컨트롤러: admin-auth.controller.ts · creator-auth.controller.ts · 가드 없음(로그인 자체가 인증 진입점)

MethodPath설명본문
POST/admins/auth/login/googleback-office 웹 idToken 로그인 → access token{ idToken }
POST/creators/auth/login/google/desktopvooth-maker 데스크톱 PKCE 로그인 → access token (CREATOR 계정 자동 생성·PENDING){ code, codeVerifier, redirectUri }

웹은 idToken 검증(verify), 데스크톱은 PKCE code 교환(exchangeCode) — 둘 다 GoogleAuthClient. maker(creators/auth)는 구현됨, tool(directors/auth)은 동일 패턴으로 예정.

05 구성요소 · 의존

  • GoogleAuthClient (infrastructure) — google-auth-library 의 OAuth2Client 래핑. verify / exchangeCode.
  • TokenService (@common/jwt) — access token 서명.
  • AccountRepository — 계정 조회/생성(AuthModule imports AccountModule).
  • ConfigsService (@configs) — Google clientId / desktopClientId / desktopClientSecret.
